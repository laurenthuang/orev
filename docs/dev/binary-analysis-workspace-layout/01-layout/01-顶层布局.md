# 2. 顶层布局

```
<workspace>/
├── README.md
├── kb/                            # 跨案件知识库（人读），见 [§10](../02-workflow/03-知识库与语料库.md)
│   ├── techniques/  signatures/  pitfalls/
├── corpus/                        # 跨案件数据资产（机器消费，可选），见 [§10](../02-workflow/03-知识库与语料库.md)
│   ├── flirt/  reference-bins/  bsim/  feature-db/
├── store/                         # 冷区：冻结的大文件；内部按 <case-id>/<type>/<target-id>/<stage>/ 镜像主树（S5）
├── tools/                         # 工具资产区：working/（项目文件）+ scripts/（共享脚本）
│   └── ghidra/
│       ├── working/<case-id>/<type>/<target-id>/{p.gpr, p.rep/}
│       ├── scripts/               # 跨 case 可复用的工具脚本（文本，进 git）
│       └── extensions/            # 插件等（可选）
│
├── cases/
│   └── <case-id>/
│       ├── CASE.md                # 要回答什么问题、结论是什么（人读入口）
│       ├── orev.toml              # 工具版本、启用阶段、保留策略
│       │
│       ├── firmware/<target-id>/  # 流水线 A：固件镜像
│       ├── binary/<target-id>/    # 流水线 B：单文件可执行 / 库
│       ├── sample/<target-id>/    # 流水线 C：恶意样本（chmod 700，见 [§13](../03-operations/03-安全与隔离.md)）
│       │
│       ├── 60_diff/               # 跨版本对比（T5），案件级；Ghidra VT 见 [§17.3](../04-appendix/02-Ghidra-12.1.4-对照.md#173-60_diff--version-tracking)
│       ├── 90_report/             # 案件级交付
│       ├── scripts/<tool>/        # 本案件专用的工具脚本（文本，进 git）
│       ├── state/
│       │   ├── index.jsonl        # 横轴：产物索引
│       │   ├── investigation.jsonl# 纵轴：线索台账
│       │   ├── checksums.jsonl    # 完整性巡检台账
│       │   └── env.md             # 环境快照（TTL 7 天）
│       └── .cache/
│
└── .gitignore
```

**三层职责**：

| 层 | 放什么 | 生命周期 |
|---|---|---|
| **workspace** | 跨案件复用：`kb/`、`corpus/`、`.gitignore` | 永久 |
| **case** | 一次分析任务：目标流水线、`60_diff`、`90_report`、`state/` | 结项后封存 |
| **target** | 单个目标的阶段流水线 | 随 case |

> `store/` 与 `tools/` 是存储区，不属于命名空间层。它们在顶层出现只表示物理位置。凡内容归属某个案件，一律用 `<case-id>` 目录段表达。这些内容在逻辑上仍属于该案件，只有实体不在主树中。

## 2.1 冷区 `store/` 与工具资产区 `tools/`

`store/` 存放冻结数据。`tools/` 按**工具**聚合该工具的全部资产：

| | `store/` 冷区 | `tools/` 工具资产区 |
|---|---|---|
| **装什么** | 产出即冻结的数据：trace、完整 PCAP、内存转储、解包文件系统 | 工具的项目文件（活）、共享脚本、插件 |
| **内部组织** | **镜像主树**：`store/<case-id>/<type>/<target-id>/<stage>/` | **按工具划分**：`tools/<tool>/{working,scripts,extensions}` |
| **读写模式** | 写入后基本只读 | `working/` 被工具频繁读写（锁、日志、快照）；`scripts/` 是纯文本 |
| **备份方式** | 可直接 `rsync` | `working/` 必须遵守 [§8.1.1](../03-operations/01-保留分级与清理.md#811-required-备份纪律) 的三条原则；`scripts/` 走 git |
| **物理位置** | `orev.toml` 的 `store_root` 声明 | `orev.toml` 的 `tools_root` 声明 |

当前 PoC 的独立案例模式支持 storage.store_root 与 storage.tools_root：省略时由初始化分别创建案例根下的默认冷区和工具区；显式配置必须指向解析后位于案例之外的现存绝对目录，初始化不创建外置根、不移动数据，也不创建符号链接。路径验证不能代替磁盘挂载检查。工具区存放工具资产，不是工具安装目录；初始化只准备根目录，不创建具体工具项目。

> **`corpus/` 与 `tools/` 的边界**（本节最易混淆的一条）：
>
> - `corpus/` 存放**跨案件复用的数据资产**：签名库、参考二进制、BSim 数据库。
> - `tools/` 存放**某个工具自身的资产**：项目文件、脚本、插件。
>
> 据此：BSim 数据库归入 `corpus/bsim/`，Ghidra 项目归入 `tools/ghidra/working/<case-id>/…`。前者一次建立、长期积累，不属任何案件；后者归属具体案件，结项时随案件带走（[§10](../02-workflow/03-知识库与语料库.md)、[§17.3](../04-appendix/02-Ghidra-12.1.4-对照.md#173-60_diff--version-tracking)）。

扩展配置设计参考见 [`schemas/orev.toml`](../schemas/orev.toml)，其中包含尚未实现的字段，不能直接作为当前 PoC 的完整配置；当前可运行配置见仓库 [README](../../../../README.md#configuration-support-current-poc)。两个根的含义：

- `tools_root`：工具工作区的物理位置。省略时使用 `<workspace>/tools/`。
- `store_root`：冷区位置，存放 trace 与 pcap。可与 `tools_root` 同盘，也可异盘。

**`tools/<tool>/` 内部的三类资产**：

```
tools/<tool>/
├── working/<case-id>/<type>/<target-id>/   # 项目文件（活，工具私有格式，required）
│   #  例：ghidra/working/router-2026q4/firmware/archerc7v5_…/{p.gpr, p.rep/}
│   #  案件级工具区与 <type> 并列：working/<case-id>/<tool>-vt/（如 Ghidra VT，[§17.3](../04-appendix/02-Ghidra-12.1.4-对照.md#173-60_diff--version-tracking)）
│   #  路径中出现工具名看似冗余（ghidra/working/<case-id>/ghidra-vt/），这是有意的：
│   #  结项后该目录脱离 tools/ghidra/ 上下文独立存在，必须具备自解释性
├── scripts/                                # 【共享】跨 case 可复用的工具脚本（文本，进 git）
└── extensions/                             # 插件（可选）
```

**脚本存放的两条规则**：

| 脚本类型 | 位置 | 理由 |
|---|---|---|
| **case / target 专用**（为本次分析编写） | `cases/<case-id>/scripts/<tool>/` | 随案件封存、进 git、保证案件自包含。结项切走时，分析逻辑一并带走 |
| **跨 case 复用**（已验证、可推广） | `tools/<tool>/scripts/` | 与工具聚合。脚本依赖工具 API，**必须记录适用版本** |

- **不为单个目标建子目录**。target-id 含 12 位哈希，长度不适合做目录名。目标专用脚本平铺存放，并用哈希前 8 位做文件名前缀，例如 `a1b2c3d4_rename_auth_funcs.py`。案件级脚本不加前缀。
  > 前缀取哈希，不取文件名头部。文件名头部不唯一：`libssl.so.1.1` 与 `libssl.so.3` 的前 8 位都是 `libssl.s`。
- **脚本自身的产出不是产物**。脚本是文本，进 git。脚本写出的内容按正常规则落入 `out/` 或 `tools/<tool>/working/`。

> **`tools/<tool>/scripts/` 中每个脚本必须在头部注释适用工具版本**（如 `# ghidra >= 12.1, API: DecompInterface`）。这与 [§10](../02-workflow/03-知识库与语料库.md) 中 BSim「更换版本后签名不可比」属同类问题。升级后失效的脚本移入 `scripts/deprecated/`，不要删除。
>
> **与 `kb/` 的关系**：`kb/techniques/` 的文章可回链 `tools/<tool>/scripts/` 中的脚本。`kb/` 说明何时使用与如何使用，脚本是配套的可执行资产。积累出可复用脚本时，按 [§14](../00-overview/02-启用档位.md) 的规则顺手补写一篇 `kb/`。

> **为什么用工具名而不是阶段名**：工具项目是跨阶段的共享工作台。Ghidra 在同一个项目中执行反编译、调试、Version Tracking 会话与 BSim 签名生成。把项目归入 `30_decompile` 属于归类错误。工具名覆盖该工具的全部用途。
>
> **case 树与 `tools/working` 的分工**：
>
> - **case 树**：存放人类可读的文本与元数据，即导出物。结构见 [§4](../01-layout/03-阶段目录契约.md)。
> - **`tools/working`**：存放工具私有格式。这类文件不被直接阅读，只被工具读写。
>
> 这条分工是 [§17.4](../04-appendix/02-Ghidra-12.1.4-对照.md#174-元数据采集program-information--落点)「元数据必须抄录为文本」原则的物理落点。需要某条信息时，从工具导出到 case 树，不要去 `working/` 中读取数据库。

> **工具工作区一律放 `tools/<tool>/working/`，不放 case 内**。未声明 `tools_root` 时，物理位置为 `<workspace>/tools/`；声明后指向外置盘。结构与路径不变，仅物理位置改变。
>
> **`path` 字段的两种前缀**。不以 `store/` 或 `tools/` 开头的路径相对**案件根**。以这两者开头的路径是**逻辑命名空间**，物理位置由 `store_root` 与 `tools_root` 决定，解析规则与 [§4.3](../01-layout/03-阶段目录契约.md#43-stageyaml-字段定义) 的 `project_dir` 一致。**主树只保留索引，不保留实体。**
>
> 前缀之后仍然写 `<case-id>` 段（`store/<case-id>/<type>/<target-id>/<stage>/`）。这不是冗余：基准虽然是案件根，但真实文件躺在 `store_root` 指向的另一块盘上，脱离了 `cases/<case-id>/` 这个天然上下文。实体离开主树，**路径就必须自解释** —— 与 [§8.1.1](../03-operations/01-保留分级与清理.md#811-required-备份纪律) 第 1 条要求备份自成一体是同一件事。
>
> **`<type>` 目录段的消费者是 `tools/` 的镜像结构**。`cases/<case-id>/<type>/<target-id>/` 与 `tools/<tool>/working/<case-id>/<type>/<target-id>/` 必须逐段对应，结项时才能整块切走（[§12](../02-workflow/05-结项封存.md)）。去掉这一层，两侧的层数就会错位，切走的将是一棵残缺的子树。
>
> 浏览分组**不是**它的用途。人工查找用 [§9.2](../03-operations/02-索引与查询.md#92-高频查询) 的查询命令，机器查找用 `index.jsonl` 的 `type` 字段。二者都不读目录名。

> 只有一个案件时，可省略 workspace 层，把 `kb/`、`store/`、`tools/` 建在案件目录旁边。
