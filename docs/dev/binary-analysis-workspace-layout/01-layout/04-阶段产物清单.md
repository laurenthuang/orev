## 5.1 工具工作区产物（`tools/` 工具资产区）

工具工作区的路径为 `tools/<tool>/working/<case-id>/<type>/<target-id>/`。案件级工具区（VT）的路径为 `tools/ghidra/working/<case-id>/ghidra-vt/<diff-name>/`。这些文件的保留级别全部为 **required**，遵守 [§8.1.1](../03-operations/01-保留分级与清理.md#811-required-备份纪律) 的备份纪律，**从不进 git**：

| 工具 | 工作区文件 | 体量 | rebuild |
| ------------------ | ------------------------------------------------------------ | ----------- | ------------ |
| **Ghidra** | `<proj>.gpr` + `<proj>.rep/` 目录 | **10–100×** | 人工批注**不可**再生 |
| **IDA** | 单个 `.i64` | 5–50× | 同上 |
| **Binary Ninja** | 单个 `.bndb` | 5–50× | 同上 |
| **radare2** | 项目目录（`prj.git=true` 时自带 git） | 1–10× | 同上 |
| **rizin** | 单个 `.rzdb`（跨版本自动迁移是单向的，[§8.1.1](../03-operations/01-保留分级与清理.md#811-required-备份纪律)） | 1–10× | 同上 |
| **Ghidra VT**（案件级） | `tools/ghidra/working/<case-id>/ghidra-vt/<diff-name>/{vt.gpr, vt.rep/}` | 5–50× | 同上 |

> **三条高频错误**
>
> 1. **认知资产位于 `tools/working/`，不在 case 内**。工具项目包含人工重命名、注释与类型定义，不可再生，保留级别为 **required** 且必须走备份。case 内 `30_decompile/out/` 的导出物删除后重跑即可恢复，保留级别为 **rebuildable**。两边的保留级别在解耦后各自成立，不要混用。
> 2. **任何对样本的修改都不得写回 `00_inbox`**。脱壳、打补丁、重建、重签名的结果一律进入 `15_patch/out/`。
> 3. **重签名产物必须记录 `signing_material`**（[§4.3](../01-layout/03-阶段目录契约.md#43-stageyaml-字段定义)）。缺少该字段时，下次无法重现同一个包。

> [§17](../04-appendix/02-Ghidra-12.1.4-对照.md) 用 Ghidra 12.1.4 完整核对了本表的落点，覆盖输入、输出、中间产物与元数据四类物件。其中 `30_decompile` 与 `60_diff` 两行有补充内容。

## 5.2 `00_inbox` 两个元数据文件的职责边界

`provenance.json` 与 `checksums.sha256` 的语义互不重叠。前者记录**外部语境**：来源与授权。后者记录**内部事实**：字节是否发生变化。

| | `provenance.json` | `checksums.sha256` |
| -------- | -------------------------------- | ----------------------------------------- |
| **回答什么** | 文件来源，以及是否有权分析 | 当前字节是否与入档时一致 |
| **谁写** | 人（或半自动），分析中**可补充** | 机器生成，**人永不编辑** |
| **会变吗** | 会。追加发现或补录授权；变化本身包含信息 | **不会**。发生变化即安全事件（[§8.3](../03-operations/01-保留分级与清理.md#83-完整性校验)） |
| **含敏感信息吗** | 是。含授权信息、内部路径、人名，**交付前脱敏**（[§13](../03-operations/03-安全与隔离.md)） | 否，可任意流转 |
| **消费方** | 人、合规审计、报告 | `sha256sum -c`、`orev verify --check`、备份校验 |

两个文件都要保留。二者记录的维度不同，任何一个都不能替代另一个。

### 不重命名，`00_inbox` 保留原始文件名

主输入即交付时获得的那个文件，文件名一字不改。

| 理由 | 说明 |
| --- | --- |
| **工具自述保真** | Ghidra 的 Program 名与 `FSRL` 取自文件名。改名后，工具项目内记录的是一个与实际来源无关的名字 |
| **多文件输入天然成立** | 固件加签名加公钥这类组合不需要额外结构 |
| **文件名可能是证据** | 钓鱼附件的命名、社工工程的话术属于取证内容 |

代价有两条，各有既定解法：

1. **命令不能写死文件名**。解法：runner 在运行前展开 `$TARGET_INPUT`，与 `$TOOLS_ROOT`、`$TARGET` 属同一套机制（[§4.3](../01-layout/03-阶段目录契约.md#43-stageyaml-字段定义)）。
2. **遍历脚本必须区分样本与元数据**。解法：读 `00_inbox/stage.yaml` 的 `input_file`。原先依赖的是「`00_inbox` 内只有四个文件」这条隐式约定，文件名不固定后该约定失效。

原名另有两处记录，不会只依赖单一位置：`input_file` 记录 `00_inbox` 内的文件名；`source.locator` 记录获得时的完整路径。两处都缺失才算信息丢失。

> **`input_file` 与 target-id 的 slug 是两件事**。target-id 中的文件名经过 slug 化（小写、去扩展名、[§3.1](../01-layout/02-目标标识.md#31-命名规则)）；磁盘上的文件保留原名。前者供目录名与查询用，后者是磁盘事实。

**`checksums.sha256` 格式纪律**：

```
a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2  ArcherC7v5_up_201229.bin
```

- **只写 sha256，与 coreutils 兼容**，保证 `sha256sum -c` 直接可用。**禁止混入其他算法**：md5 长度的行会导致 `-c` 报错。
- **行内写 `00_inbox` 中的实际文件名**，取值等于 `stage.yaml` 的 `input_file`。该文件由 `sha256sum -c` 就地消费，文件名必须与磁盘一致。
- **命令里禁止手工拼接文件名**。一律使用加引号的 `$TARGET_INPUT`（[§4.3](../01-layout/03-阶段目录契约.md#43-stageyaml-字段定义)）。原始文件名不可控，实测四例格式均会破坏命令：`Archer C7 v5.bin`（空格，bash 未加引号时被切成三个参数）、`-rf-x.bin`（前导短横，相对路径下被解析为选项）、`更新包(最终版)v2.img`（括号，未转义时 `sh: Syntax error: "(" unexpected`）、`$(…).elf`（命令替换元字符）。
- 多个输入文件时逐行列出，`checksums.sha256` 天然支持多行。
- 替代哈希（md5 / sha1，用于对接威胁情报与样本库）写入 `provenance.json` 的 `source.alt_hashes`。这些信息属于来源语境。

**`provenance.json` schema**：

样例见 [`schemas/provenance.json`](../schemas/provenance.json)。要点：

- `source` 记录来源类型、定位符、声明版本与替代哈希。
- `authorization` 记录授权凭证、范围与有效期。
- `chain_of_custody` 是追加列表。每次交接追加一条。

- **不写 sha256 字段**。完整哈希由同目录的 `checksums.sha256` 承载。重复记录会引入第二处漂移源。
- `declared_version` 记录**来源声明的**版本。它与 `headers.json` 中识别出的版本并存，且允许不一致。不一致本身是有价值的发现（[§3.2](../01-layout/02-目标标识.md#32-四条硬规则) 第 2 条）。

**单一权威原则**：同一个 sha256 会出现在多处。权威链如下：

```
00_inbox/checksums.sha256   （权威：真正被 `sha256sum -c` 消费的那一份）
  └─ index.jsonl / manifest.json / stage.yaml   （全部是引用，不重新计算）
```

**三个校验文件的分工**（文件名相似，用途不同）：

| 文件 | 是什么 | 生成时机 |
| ------------------------------------ | ------------------------ | ------------------- |
| `00_inbox/checksums.sha256` | **入档快照**：这个 target 的原始指纹 | 入档时一次，之后只读 |
| `state/checksums.jsonl` | **巡检台账**：每次校验的记录（含时间戳） | 每次分析前后 / 季度巡检（[§8.3](../03-operations/01-保留分级与清理.md#83-完整性校验)） |
| `90_report/out/evidence/<F-xxx>/checksums.sha256` | **交付副本**：证据包内全部文件的校验和 | 生成证据包时（[§6.5](../02-workflow/01-证据契约.md#65-证据导出吸收-reark-的-copy-evidence)） |
