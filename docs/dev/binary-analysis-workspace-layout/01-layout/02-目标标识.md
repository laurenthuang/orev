# 3. 目标标识（target-id）

## 3.1 命名规则

```
<文件名>_<sha256[:12]>
```

target-id 只承担两项职责：标识文件名，标识文件内容。架构、版本、格式均不进 target-id。理由见 [§3.2](#32-四条硬规则) 第 2 条。

| 类型   | 原始文件名                      | target-id                           |
| ---- | -------------------------- | ----------------------------------- |
| 固件   | `ArcherC7v5_up_201229.bin` | `archerc7v5_up_201229_a1b2c3d4e5f6` |
| 单文件  | `nginx-1.24.0`             | `nginx-1.24.0_9f8e7d6c5b4a`         |
| 恶意样本 | `9c1f8e2a7b34`             | `9c1f8e2a7b34_7c1d9e2fa4b6`         |

**`<文件名>` 的 slug 化规则**（生成一次，之后固定）：

| 变换                               | 例                                                   |
| -------------------------------- | --------------------------------------------------- |
| **去掉扩展名**                        | `ArcherC7v5_up_201229.bin` → `ArcherC7v5_up_201229` |
| 转小写                              | → `archerc7v5_up_201229`                            |
| 空白（含连续）→ `-`                     | `Archer C7 v5.bin` → `archer-c7-v5`                 |
| 删除非法字符与控制字符：`/ \ : * ? " < > \|` | `a:b/c.bin` → `abc`                                 |
| 首尾 `-` `_` 修剪                    | `_foo_` → `foo`                                     |
| 超 **48** 字符截断（取头部）               | 长名 → 前 48 字符，靠哈希保证唯一                                |

> **slug 化的产物只用于目录名。** `00_inbox` 内的文件保留原始文件名，不改名（[§5.2](../01-layout/04-阶段产物清单.md#52-00_inbox-两个元数据文件的职责边界)）。上表的变换把不可控的文件名收敛为可安全用作路径的目录名，磁盘上的文件本身不受影响。

> **为什么要去掉扩展名**：扩展名是未经核实的自我声明。`firmware.bin` 的实际格式可能是 squashfs，`libssl.so` 可能是 ELF，也可能只是文本。真实格式由 `20_static` 判定，并写入 `headers.json`（[§17.4](../04-appendix/02-Ghidra-12.1.4-对照.md#174-元数据采集program-information--落点)）。这与「架构、版本要在分析后才知道」是同一条原则：target-id 中不放尚未验证的信息。

**解析规则**：使用正则 `^(?P<name>.+)_(?P<hash>[0-9a-f]{12})$`。`name` 采用贪婪匹配，即以**最后一个** `_` 分隔。文件名中原有的 `_` 不影响解析。

> **全文示例统一使用上表的三个 target-id**：固件 `archerc7v5_up_201229_…`、单文件 `nginx-1.24.0_…`、样本 `9c1f8e2a7b34_…`。哈希后缀恒为 12 位。出现其他形态即为错误。  
> 以版本号为例：`ArcherC7v5_up_201229.bin` 官网声明的版本是 `1.2.3`。该值**只出现在 `provenance.json` 的 `declared_version`**（[§5.2](../01-layout/04-阶段产物清单.md#52-00_inbox-两个元数据文件的职责边界)），不进目录名。

## 3.2 四条硬规则

1. **哈希后缀是权威标识**。文件名可能重复，版本字符串可能缺失，SHA256 前 12 位不会重复。完整哈希由 `00_inbox/checksums.sha256` 承载（[§5.2](../01-layout/04-阶段产物清单.md#52-00_inbox-两个元数据文件的职责边界)）。内容寻址依赖记录的哈希字段，不依赖目录名。目录名无法表达「两个 target-id 不同但内容相同」这种情况。
2. **架构、版本、格式不进 target-id**。理由有三条：
   - **开案时无法确定**。拿到一个裸样本时，架构与版本通常未知。把它们写进 target-id 会迫使使用者在建目录时先猜测取值。
   - **分析结果可能推翻初始值**。识别结果与初始假设不一致时，改目录名会使所有引用该路径的记录失效，包括 `index.jsonl`、`manifest.json`、`stage.yaml`。
   - **两类信息可能冲突**。来源声明的版本（`provenance.json`）与二进制中识别出的版本（Ghidra、strings）常常不同。这种不一致本身是有价值的发现。把版本写进目录名会迫使使用者二选一。

     **落点**（信息不丢失，只是从目录名迁移到元数据）：

| 信息               | 落点                                              | 确定时机                                                                                                     |
| ---------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 格式 / 架构 / endian | `20_static/out/headers.json`                    | 分析后（readelf 与 Ghidra 互校，[§17.4](../04-appendix/02-Ghidra-12.1.4-对照.md#174-元数据采集program-information--落点)） |
| **声明的**版本        | `00_inbox/provenance.json` → `declared_version` | 入档时                                                                                                      |
| **识别出的**版本       | `20_static/out/headers.json`                    | 分析后                                                                                                      |
| 人类可读描述           | `CASE.md` 目标清单                                  | 开案时                                                                                                      |
| 检索标签             | `index.jsonl` 的 `tags`：`arch=`、`version=`       | 索引时                                                                                                      |

> 差分分析仍然需要版本信息。获取方式从「解析目录名」改为「读取 `headers.json` 与 `provenance.json`」。见 [§3.2](#32-四条硬规则) 第 4 条。

1. **target-id 生成后不得修改**。内容变更时新建 target-id，旧目录保持原样。这是 T4 幂等的前提。
2. **版本关系由 `orev.toml` 的 `[[diff]]` 显式声明，不依赖 target-id 解析**。target-id 不含版本段，因此无法自动判断两个目标是否为同一系列的前后版本。该信息改由配置声明（[§4.2](../01-layout/03-阶段目录契约.md#42-阶段编号)）。`60_diff` 读取配置，不猜测命名。

## 3.3 固件内部组件

固件解包后可能产生数百至数千个文件。**不要为每个组件建立顶级目录**。组件作为次级目标，在后续阶段的 `out/` 下按路径 slug 分桶：

```
30_decompile/out/
├── usr_sbin_httpd/          # /usr/sbin/httpd → usr_sbin_httpd
├── usr_bin_busybox/
└── lib_libc.so.0/
```

slug 规则：去掉前导 `/`，其余 `/` 与 `.` 替换为 `_`；超过 64 字符时取头部并追加内容哈希前 8 位。

> **只在阶段产出按组件分组时才建立 `<slug>/` 桶**（固件解包、单个项目含多个 program）。单文件目标（一个 ELF、一个 PE）**直接平铺在 `out/`**。层级结构的价值随组件数量增长，组件数为 1 时该层级只是噪音。同理，[§16](../04-appendix/01-落地检查清单.md) 中的 `component=` 标签在单文件场景下指整个文件本身，可省略。

> **例外：`60_diff` 在一组时也必须分桶。** `orev.toml` 只需追加一条 `[[diff]]` 就会产生第二组对比。此时若没有 `<diff-name>/` 桶，第二组的 `diff-report.html` 会覆盖第一组，而那是 permanent 级产物。**补一层结构的成本在开案时，改结构的成本在事后** —— `index.jsonl`、`manifest.json`、`stage.yaml` 全都记录了路径，事后迁移要同时改三份。
>
> 上一段的规则适用于「事后才发现需要分层也不痛」的场景。`60_diff` 不属于这类场景。该例外只适用于 `60_diff`。

> **两处 slug 是同一套变换、两档阈值**：target-id 的文件名 slug 先去扩展名，阈值 **48**（[§3.1](#31-命名规则)）；组件分桶 slug 保留 `.` 并映射为 `_`，阈值 **64**（本节）。判断依据是上下文：顶层 `firmware|binary|sample/<…>` 用前者，`out/` 下的分桶用后者。
