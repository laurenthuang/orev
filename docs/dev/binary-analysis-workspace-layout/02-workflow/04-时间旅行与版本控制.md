# 11. 时间旅行与版本控制（T6 落点）

T6 没有落点就无法落地。本规范用三层机制实现：

| 层 | 机制 | 说明 |
| ------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **工具级** | 用工具自带的版本能力 | Ghidra **快照 / 版本历史**（`.rep/versioned/`，**仅私有非共享项目**）；radare2 设 `prj.git=true`，使每个项目自带 git；rizin 项目是单文件 `.rzdb`，按日期保存多份（⚠️ 跨版本自动迁移是单向的，见 [§8.1.1](../03-operations/01-保留分级与清理.md#811-required-备份纪律)）；IDA / Binary Ninja 手动保存多份 `.i64` / `.bndb`，并带日期后缀 |
| **案件级** | 整个 case 纳入 git | **只提交 permanent 与索引**，大文件走 `.gitignore`；关键节点打 tag |
| **认知级** | `investigation.jsonl` 的 `dead_ends` | 记录已排除的路径，避免重复尝试。这是成本最低的回滚方式 |

## 打 tag 的时机

命令见 [`scripts/git-tagging.sh`](../scripts/git-tagging.sh)。

**规则**：`20_static` / `30_decompile` / `50_findings` 每个阶段 `status: ok` 时打一次 tag。tag 名带案件前缀，便于跨案件筛选。

> **radare2 的 `prj.git=true` 是最轻量的实现**。项目保存时自动提交，省去手工快照的执行成本。Ghidra 用户使用**快照 / 版本历史**（`versioned/`）。
>
> ⚠️ **纠错**：「Ghidra 用户使用内置 Version Tracking」的说法不正确。**Version Tracking 不是时间旅行工具**。它比较两个**不同的程序**，典型场景是同一软件的两个版本，属于 **T5 差分**，落点在 `60_diff`（[§17.3](../04-appendix/02-Ghidra-12.1.4-对照.md#173-60_diff--version-tracking)）。同一程序的历史回退使用快照功能。两者名称都含 Version，容易混淆：前者横向比较两个文件，后者纵向比较同一文件的历史。
